# DynaPin Tree配置最適化の高速化検証（2026-10-10）

## 変更

- Treeの計測器を生成ごとのローカル状態とし、主要ステージだけを `std::chrono::steady_clock` で測る。衝突・回避領域取得などの細粒度計測を除去。
- 枝径係数を `TreeSupportData` に所有させ、ノード生成へ渡す。従来の係数式を維持。
- Treeの角度群並列数を1に強制する処理を削除。既存のCPU・メモリ制御、キャンセル、進捗同期を利用。
- 探索間隔、候補数、採点、同点判定、ピン棄却と再生成、ツールパス生成と着地検証は変更していない。

## 性能比較

macOS arm64 / Release / Xcode 26.4.1。`TZ` は設定せず、通常のローカル時刻環境を使用。

`tests/data/dynapin/Simple_Bridge.3mf` を使う既存テスト `DynaPin Tree bounded placement keeps Simple Bridge support pins` を比較。元姿勢と355度に探索範囲を制限した126候補の評価で、並列数は変更前後とも1。全面探索や自動並列化の性能値ではない。

比較用に `run_placement_task()` と、採用姿勢を適用した `Print::process()` の前後へ一時的なsteady_clock計測を入れ、変更前・変更後のソースをそれぞれ再ビルドして各3回実行した。CPU時間とピークRSSは各プロセスの `wait4()` で取得。一時計測は製品・テストの最終ソースから除去した。

候補探索の中央値は **11.660秒 → 1.255秒（9.29倍、89.2%短縮）**。目標の半分以下を満たした。最終スライスの中央値は0.422秒 → 0.082秒。

変更前後の全試行で採用角度355度、Y移動0、候補評価数126、評価体積2316.73 mm³（診断表示精度）、最終ピン `1,5 1,6 1,7` が一致した。

**上記の既存テストは変更前後とも、最終サポート経路の確認中に `Coordinate outside allowed range` で失敗（14/15アサーション成功）した。** 探索と最終スライスは完了してから例外が発生しているが、この計測を回帰テストの成功としては扱わない。

## 回帰検証

Releaseで `libslic3r_tests`、`fff_print_tests`、`OrcaSlicer` をビルド。配置・資源制御テストは24件/122アサーションすべて成功。FFF DynaPin回帰テストは28件中27件成功、311アサーション中310成功。新規4件はすべて成功。新規検証は以下を含む。

- Treeタスクで並列数1・2・自動が実際に尊重され、採用候補と評価数が一致する。
- Tree Slim・Strong・Hybridと枝径角度5度・25度の6種類を並行評価し、逐次評価と候補の有効性・評価体積が一致する。
- Simple Bridgeの限定探索で、並列数1・2・自動の採用位置・角度、評価体積、評価数、最終ピン集合とサポート押出体積が一致する。各Printのプレート原点を明示的に設定し、採用後のフルスライスを実行する。
- 別オブジェクトの枝径係数が並行ノード生成でも混ざらない。

既存の配置テストはキャンセル、メモリ待機・復帰、資源サンプリング失敗、bad_alloc、進捗の同期・単調増加を含む。FFFのDynaPinテストはNormal、DynaPin無効時のTree、ピン棄却を含む。

変更前のFFF DynaPinテスト全体でも `DynaPin Tree selects pins after applying an optimized pose` は期待3ピンに対して1ピンとなる不一致で失敗。変更後も同じ失敗を確認した。既存の失敗として記録し、今回の成功件数には含めない。

## 検証範囲の制限

並列数の自動調整を実モデルで比較するテストは、他アプリのメモリ使用量に左右されないよう十分な資源を返すプローブを使用する。実際の低メモリ時の保護は既存スケジューラのテストで確認する。新規のフルスライス比較テストでは、Printのプレート原点の未初期化を修正して同値性を確認した。既存のSimple Bridge関連テスト3件でもプレート原点を明示的に設定した。測定に使った既存限定探索テストも、最終ソースでは成功している。上記性能表は初期化修正前の共通終了点での比較であり、候補探索部分と区別して扱う。GUIでの実操作、全面探索の性能測定、実機造形は未実施。

実行コマンド：

```sh

build/arm64/tests/libslic3r/Release/libslic3r_tests.app/Contents/MacOS/libslic3r_tests "[DynaPinPlacement]" --reporter compact
build/arm64/tests/fff_print/Release/fff_print_tests.app/Contents/MacOS/fff_print_tests "[DynaPin]~[.]" --reporter compact
```

## 実GUIで5%付近にとどまる報告の追調査

2026-10-10 03:10開始のGUIログで、`RemoveGymnastBase.stl`（331層）を確認。削除済みの細粒度項目を含まないTree計測ログから、修正版が実際に動いていることを確認した。03:12:27時点でTree生成60回、中央値114.5ms。候補の自動ピン選択は直近のobject scan開始からselection resolvedまで約2.7〜6.4秒かかっており、Simple Bridgeとは負荷の構成が異なる。この区間の時間はログ境界による概算で、選択内部の関数別プロファイルではない。

03:11:25に `waiting for memory` を確認。実機は16GiBで予約量は3.2GiB、ログの利用可能量は3,855,253,504バイト。予約後の余裕は419,279,667バイトで、次の角度群の最低見積り536,870,912バイトを下回る。したがって、角度群を追加せずに待機する。03:11:34以降には別スレッドで候補計算が再開しており、完全な停止ではない。進捗率は全候補数に対する完了数の整数百分率なので、少数候補の完了では表示が変わらない。

Tree固有の逐次上書きを削除したことで、従来Treeが通らなかった自動スケジューラのメモリ待機条件が適用されるようになった。固定並列数・十分な資源を返すテストプローブでの検証は、この実機条件の待機時間を検証していなかった。9.3倍という測定値を、このモデルのGUI探索全体の性能保証として扱わない。待機中もCPU利用率が低いと並列目標だけが増える制御もログで確認したが、メモリ許可なしに起動することはない。
